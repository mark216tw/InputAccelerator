# 系統設計文件

本文件說明「輸入加速」的設計目標、需求、關鍵設計決策、狀態流程與品質考量。技術實作細節請搭配 [系統架構與技術文件](ARCHITECTURE.md) 閱讀。

## 1. 文件目的

- 記錄產品與技術設計的共識，作為後續維護與擴充的依據。
- 說明重要取捨與已知限制，避免未來修改破壞既有行為。
- 提供測試與驗收的參考脈絡。

## 2. 產品定位

### 2.1 問題陳述

使用者在日常工作經常需要重複輸入相同文字，例如：

- 客服或業務的制式回覆。
- 表單中的地址、統編、Email、簽名檔。
- 程式開發常用的程式碼片段或指令。
- 多步驟流程中需要反覆貼上的內容。

現有做法通常是切換視窗、開啟文字檔、複製貼上，流程中斷且效率低。

### 2.2 解決方案

提供一個常駐 Windows 桌面的小工具：

1. 集中管理常用文字。
2. 以永遠置頂的浮動視窗快速存取。
3. 點擊即可輸入到目前游標位置。
4. 不干擾目標程式焦點與工作流程。
5. 記住視窗位置與外觀設定。

### 2.3 目標使用者

- 需要高頻率輸入固定文字的辦公室與客服人員。
- 開發者、測試人員與系統管理者。
- 使用 Windows 10／11，包含 x64 與 Arm 裝置的使用者。

### 2.4 非目標

- 不做雲端同步或跨裝置帳號系統。
- 不做團隊共享或權限管理。
- 不提供安裝檔、自動更新或市集發佈。
- 不支援 macOS、Linux 或行動裝置。
- 不處理圖片、富文字或檔案貼上。

## 5. 使用案例

### UC-01 新增常用文字

1. 使用者開啟主視窗。
2. 點擊「新增」。
3. 在對話框輸入多行文字。
4. 按「儲存」。
5. 清單與浮動視窗同步出現新項目。
6. 程式非同步儲存 `entries.json`。

### UC-02 快速輸入文字

1. 使用者在目標程式（例如記事本）放置游標。
2. 點擊浮動視窗中的文字膠囊。
3. 程式還原目標視窗焦點。
4. 依輸入模式送出文字。
5. 目標程式收到文字。
6. 若失敗，系統匣顯示提示。

### UC-03 調整浮動視窗

1. 使用者拖曳頂端把手移動視窗。
2. 或拖曳右下角把手調整大小。
3. 停止操作 500ms 後，程式儲存位置與大小。
4. 下次啟動時還原，若超出工作區則自動修正。

### UC-04 切換外觀

1. 使用者點擊 More。
2. 在設定視窗選擇顯示模式與背景色。
3. 三個視窗即時套用新主題。
4. 設定寫入 `settings.json`。

### UC-05 從系統匣操作

1. 使用者關閉主視窗，程式縮到系統匣。
2. 點擊系統匣圖示顯示主視窗。
3. 可從選單切換浮動視窗或結束程式。

## 6. 關鍵設計決策

### 6.1 為何使用 WinUI 3 與 Windows App SDK

- 原生 Fluent 控制項與現代 Windows 視覺一致。
- 支援 Windows 10 1809 以上與 Windows 11。
- 可與 Win32 interop 搭配，滿足置頂、不搶焦點與系統匣需求。

代價是免安裝版需安裝 Windows App SDK Runtime，且建置流程比純 WPF 複雜。

### 6.2 為何採 framework-dependent 發佈

- 大幅縮小 zip 體積。
- 使用者可共用系統上的 Windows App SDK Runtime。
- 符合本專案「不提供安裝檔」的定位。

代價是首次使用需安裝 Runtime。若未來需要完全免安裝，可另提供 Self-Contained 版本。

### 6.3 為何浮動視窗不搶焦點

若浮動視窗取得焦點，點擊時原本的目標視窗會失去焦點，輸入將送到錯誤位置。因此採用：

- `WS_EX_NOACTIVATE`：點擊時不啟用視窗。
- `WS_EX_TOOLWINDOW`：不顯示在 Alt+Tab。
- `Show(activateWindow: false)`：顯示時不啟用。
- 追蹤最近一個外部前景視窗，點擊後必要時還原焦點。

這是本產品最核心的互動設計。

### 6.4 為何提供兩種輸入模式

- 模擬鍵盤輸入不佔用剪貼簿，適合大多數情境。
- 部分終端機、遊戲或特殊程式不處理 Unicode 模擬輸入，需改用剪貼簿貼上。
- 讓使用者可依程式相容性切換，而不是強制單一方案。

### 6.5 為何使用 JSON 而非資料庫

- 資料量小（數十到數百筆文字）。
- 需要容易備份、檢視與手動修復。
- 避免引入 SQLite 與 EF Core 的額外相依與體積。
- 以暫存檔原子替換與損壞檔備份維持可靠性。

若未來資料量或查詢需求增加，可替換 Core 的 Repository 實作。

### 6.6 為何將 Core 獨立成類別庫

- 讓模型、序列化、文字組合與位置驗證可在一般 .NET 測試專案驗證。
- 避免 UI 與 Win32 相依污染核心邏輯。
- 降低未來替換 UI 框架的成本。

### 6.7 為何收合狀態不持久化

- 收合是短暫的螢幕空間調整，不是長期偏好。
- 重新啟動時以展開狀態呈現，可避免使用者忘記自己曾收合而找不到視窗。
- 降低位置儲存狀態機的複雜度。

## 7. 系統狀態與流程

### 7.1 應用程式生命週期

```text
啟動
  → 單一實例檢查
      ├─ 已有執行個體 → 廣播啟用訊息 → 結束
      └─ 取得 Mutex
          → 建立 DI/Host
          → 載入設定與文字
          → 初始化系統匣與視窗
          → 顯示主視窗
          → 常駐
              ├─ 關閉主視窗 → 隱藏到系統匣
              ├─ 關閉浮動視窗 → 隱藏浮動視窗
              └─ 系統匣結束 → 儲存資料 → 結束
```

### 7.2 浮動視窗狀態

```text
隱藏 ⇄ 展開 ⇄ 收合
  │       │        │
  │       │        └─ 點擊小區塊 → 還原展開位置
  │       └─ 點擊「－」→ 儲存展開位置 → 縮成 56 DIP
  └─ 主視窗開關或系統匣切換
```

規則：

- 收合時不寫入小區塊尺寸。
- 收合時停用調整大小。
- 收合時不提供拖曳移動。
- 還原時套用收合前位置與大小。

### 7.3 輸入流程

```text
點擊膠囊
  → 解析目標視窗
      ├─ 找不到 → 提示失敗
      └─ 找到
          → 必要時還原焦點
          → 再次確認前景
              ├─ 失敗 → 提示失敗
              └─ 成功
                  → 模擬輸入或剪貼簿貼上
                      ├─ 成功 → 完成
                      └─ 失敗 → 提示失敗（5 秒節流）
```

### 7.4 設定變更流程

```text
變更顯示模式／背景／輸入模式／浮動視窗開關
  → MainViewModel 更新
  → SettingsService.Current 更新
  → 立即套用（外觀或視窗顯示）
  → 非同步儲存 settings.json
```

## 8. 資料設計

### 8.1 實體

```text
TextEntry
  Id: Guid
  Content: string

AppSettings
  IsOverlayEnabled: bool
  InputMode: SimulatedInput | ClipboardPaste
  Theme: System | Light | Dark
  FloatingBackgroundIndex: int（0 = 跟隨系統，1..12 = 固定色）
  FloatingWindowPlacement: WindowPlacement?

WindowPlacement
  X, Y, Width, Height: int（像素）

DisplayAreaInfo
  MonitorArea: PixelRect
  WorkArea: PixelRect
```

### 8.2 驗證規則

- `TextEntry.Content` 不可為空白；儲存時過濾空白項目。
- `TextEntry.Id` 為空或重複時重新產生 GUID。
- `InputMode`、`Theme` 必須是有效列舉值，否則回到預設。
- `FloatingBackgroundIndex` 必須介於 0 與 12。
- `WindowPlacement.Width`、`Height` 必須大於 0，否則視為無效。
- 視窗位置與尺寸最終由 `WindowPlacementValidator` 限制在工作區與最小尺寸內。

### 8.3 資料相容性

- JSON 使用 camelCase，讀取時忽略大小寫。
- 新增欄位時採「缺少即使用預設」策略。
- 列舉以字串儲存，避免重新排列數值造成誤解。
- 讀取失敗時備份原始檔案，不以預設值覆寫。

## 9. 錯誤處理與復原

| 情境 | 處理方式 |
| --- | --- |
| `entries.json` 損壞 | 改名為 `.bad-<時間戳>`，以空清單啟動 |
| `settings.json` 損壞 | 使用預設設定 |
| 磁碟寫入失敗 | 記錄錯誤，UI 顯示之資料仍在記憶體中 |
| 找不到目標視窗 | 系統匣氣球提示 |
| 無法還原焦點 | 記錄警告並提示失敗 |
| `SendInput` 被拒 | 提示使用者改用剪貼簿模式 |
| 系統匣圖示遺失 | 監聽 `TaskbarCreated` 重新加入 |
| 未處理例外 | 寫入日誌並結束程式 |

## 10. 效能與資源考量

- 拖曳與調整大小期間不寫入磁碟，停止 500ms 後才儲存。
- 檔案 I/O 使用非同步 API，不阻塞 UI。
- 文字輸入分批送出，降低 `SendInput` 佇列壓力。
- 輸入失敗提示有 5 秒節流，避免氣球洗版。
- 設定視窗為 singleton，關閉只隱藏，降低重複建立成本。
- 浮動視窗項目使用 `ItemsControl` 與自訂 `WrapPanel`，避免 `ListView` 的額外互動負擔。

## 11. 安全性與隱私

- 程式不進行任何網路連線。
- 日誌不記錄使用者文字內容。
- 文字資料僅存放於目前使用者的 `%AppData%`。
- 不要求系統管理員權限；但若目標程式以管理員權限執行，需以相同權限啟動才能模擬輸入。
- 剪貼簿模式會覆蓋目前剪貼簿內容，使用前應提醒使用者。
- 不包含簽章憑證或任何金鑰。

## 12. 測試與驗收

### 12.1 自動化測試

- Core 邏輯以 xUnit 覆蓋。
- 建置時啟用 `TreatWarningsAsErrors`。
- 以 `dotnet format --verify-no-changes` 維持格式一致。

### 12.2 手動驗收清單

- [ ] 新增、編輯、刪除、排序文字後，浮動視窗同步更新。
- [ ] 在記事本輸入中文、英文、多行與 Tab。
- [ ] 在瀏覽器與 Word 輸入文字。
- [ ] 切換剪貼簿模式並確認目標程式收到文字。
- [ ] 拖曳移動與調整大小後重新啟動，位置與大小正確還原。
- [ ] 更換螢幕解析度或 DPI 後，浮動視窗仍在可見範圍。
- [ ] 收合與還原位置正確。
- [ ] 顯示模式與背景色即時套用，重啟後保留。
- [ ] 關閉主視窗後可從系統匣重新開啟。
- [ ] 重複啟動只帶回既有主視窗。
- [ ] 以管理員權限目標程式測試輸入行為。
- [ ] x64 與 arm64 版本皆可啟動。

## 13. 風險與限制

| 風險 | 影響 | 緩解方式 |
| --- | --- | --- |
| Windows App SDK Runtime 未安裝 | 程式無法啟動 | 文件明確說明需求；必要時另提供 Self-Contained |
| 特殊程式不接受模擬輸入 | 無法輸入 | 提供剪貼簿模式 |
| 系統管理員權限差異 | 模擬輸入被拒 | 文件說明需相同權限 |
| Windows 10 無 DWM 圓角 | 視覺不一致 | 視為可接受限制 |
| 多螢幕與 DPI 變化 | 視窗位置錯誤 | 啟動時驗證並修正位置 |
| 剪貼簿被覆蓋 | 使用者資料遺失 | 文件提醒；未來可考慮備份／還原剪貼簿 |
